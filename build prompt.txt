# CODEX MASTER BUILD PROMPT — TIPS DECK

Build a production-ready football prediction platform called **Tips Deck**.

Tips Deck should operate similarly to A1Tips in terms of business flow, but it must have an original design, original code, better usability, cleaner architecture, better transparency, and a stronger modern product experience.

Do NOT copy A1Tips branding, content, code, layout, images, text, or proprietary assets.

Use A1Tips only as a functional reference for:

- free football predictions
- yesterday / today / tomorrow predictions
- VIP/premium predictions
- user accounts
- premium access
- results history
- prediction performance
- social/Telegram funnel
- daily publishing of tips

Tips Deck should feel like a **modern football intelligence product**, not a cluttered gambling website.

---

# IMPORTANT DEVELOPMENT RULE

DO NOT build the entire application in one pass.

Build Tips Deck in clearly separated stages.

At the end of each stage:

1. run TypeScript checks
2. run lint
3. run tests relevant to that stage
4. run the production build
5. fix all errors
6. summarize what was completed
7. stop and wait for the next instruction before starting the next stage

Do not move automatically to later stages.

The goal is to keep the codebase stable and reviewable throughout development.

# 6. DAILY FOOTBALL DATA MODEL

Tips Deck should NOT require the administrator to manually type every football fixture.

The system should support integration with a licensed football-data API.

Examples:

- API-Football
- SportMonks
- Football-Data
- another configurable provider

Create an abstraction:

```ts
export interface FootballProvider {
  getFixturesByDate(date: string): Promise<FixtureInput[]>
  getFixtureById(id: string): Promise<FixtureInput | null>
  getResultsByDate(date: string): Promise<FixtureResultInput[]>
  getLeagueStandings?(leagueId: string): Promise<StandingInput[]>
  getHeadToHead?(homeTeamId: string, awayTeamId: string): Promise<MatchInput[]>
}
```

Create:

```text
lib/football/
├── provider.ts
├── mock-provider.ts
├── types.ts
└── sync.ts
```

Use the mock provider until a real API key is configured.

Never scrape sports websites.

# 7. FIXTURE SYNCHRONISATION

The system should be able to automatically sync:

- yesterday
- today
- tomorrow
- several upcoming days

Store fixtures locally in PostgreSQL.

Do NOT fetch the external football provider every time a visitor loads a page.

The website should read from PostgreSQL.

Architecture:

```text
Football API
    ↓
Scheduled Sync
    ↓
PostgreSQL
    ↓
Tips Deck Website/Admin
```

Create a secure cron-compatible endpoint such as:

```text
/api/cron/sync-fixtures
```

Protect it using a secret.

The sync should:

- insert new fixtures
- update changed fixtures
- avoid duplicates
- update kickoff times
- update fixture status
- update final scores
- preserve existing predictions

Use provider fixture IDs as external identifiers.
